## 1. Executive Summary

Build System News: a centralized news platform that ingests approved publisher feeds, scores and dedupes them, writes one short original summary per story in its own language, and serves five themed industry sites plus a versioned public API. Delivery is eight milestones (M1-M8), each shippable and independently verifiable. Stack is fixed by ADRs 001-012: Python 3.12/FastAPI, PostgreSQL 16, Redis 7, Next.js 15, single VPS with Compose and Caddy. Content is language-partitioned (EN unprefixed, `/es`), never translated; AI summaries use DeepSeek `deepseek-flash`; refresh runs twice daily by default with manual force. The first three milestones carry most risk: protected-file scaffold, schema correctness, and the ingestion pipeline. Copyright, Spanish coverage, and single-host availability are the residual risks.

## 9. Architecture Overview

Cite `.work/plans/foundation/20261105-04-foundation-architecture.md` §2-§4. Summary:

```
web (Next.js SSR/ISR) ──HTTP──▶ publishing ──▶ articles/channels/sources (ports)
editorial (admin) ─────HTTP──▶ articles/channels/sources (ports)
worker ──Redis Streams──▶ articles (fetch/score/summarize)
publishing/editorial/articles/sources/channels ──▶ platform (db, cache, i18n, security)
```

- **Deployment unit:** one Compose stack (`caddy`, `web`, `api`, `worker`, `postgres`, `redis`).
- **Boundaries:** contexts import only `platform` and other contexts' `ports`; no shared ORM models.
- **Read path:** request → locale/industry resolution → `publishing` query → `ArticleQueryPort` (language + channel + window) → DTO → cache/ETag.
- **Lead path:** CTA → `POST /v1/leads` → `leads` + `lead_events` → partner notification → admin inbox.
- **Write path:** scheduler/manual → Redis Stream → worker → fetcher → normalize → partition → score/dedupe → persist → AI → bundle cache invalidation.

**Diagram of milestone dependency:** M1 → M2 → M3 → M4 → M5 → M6 → M7 → M8 (M5 can start after M2 with fixtures; M6 after M5).

## 11. Data Strategy

- PostgreSQL 16 as source of truth (ADR 002); Redis is disposable (ADR 003).
- Schema: `industries`, `industry_locales`, `sources`, `topics`, `articles`, `article_topics`, `pins`, `api_keys`, `contact_messages`, `partners`, `leads`, `lead_events`, `cta_events`, `refresh_runs`, `audit_events` (doc 04 §4).
- **Migrations:** numbered idempotent SQL under `apps/api/migrations/`, applied at API start by `news_api.platform.migrations`; run twice in CI to prove idempotency.
- **Retention:** 7-day display window, 30-day row purge, 90-day contact purge, 30-day backups, 14-day logs.
- **Search:** Postgres `tsvector` generated column + GIN behind `SearchPort`.
- **No full text/media** persisted (copyright).

## 12. Security Strategy

- Threat model: `.work/standards/20261105-threat-model.md` (T1-T12); data classes: `20261105-data-classification.md`.
- AuthN/Z: public reads keyless (rate-limited), API keys hashed (SHA-256+pepper), admin JWT (HS256, 15 min) + Argon2id + CSRF double-submit (ADR 011).
- Lead PII: consent version + timestamp, peppered IP/UA hashes, 24-month retention, no PII in logs/analytics, DSAR export/erase (ADR 013).
- Input safety: Pydantic validation, HTML sanitization at ingest, React escaping, CSP, SSRF-guarded fetcher.
- Secrets: env only; `.env*` ignored; no secrets in logs, docs, or fixtures.
- Abuse: Redis rate limits, cursor/limit caps, contact honeypot.
- Review: security checklist at M8-T4; cross-model review before enabling production credentials.

## 13. Infrastructure Strategy

- Single VPS, Docker Compose (`docker-compose.dev.yml`, `docker-compose.prd.yml`), Caddy TLS + reverse proxy (ADR 005).
- Environments: `dev` (local), `stg` (optional, `STACK_SUFFIX=stg`), `prd`.
- Ports (dev): web 3000, api 8080, postgres 5433, redis 6380, prometheus 9090, grafana 3001; prd publishes only 80/443.
- Volumes: `pgdata`, `redisdata`, `caddy_data`, `caddy_config`.
- Backup destination: off-site bucket (provider at O3); encrypted volume `.tar.gz` snapshots, 30-day lifecycle.

## 14. Deployment Strategy

- GitHub Actions: `ci.yml` (PR), `build.yml` (main images), `deploy.yml` (manual dispatch, SSH).
- Images tagged `sha-<short>` + `latest`; deploy pins a SHA; rollback re-deploys previous SHA.
- Migrations run at API start; deploy waits for `/v1/health`.
- Staged rollout: prd deploy → health → smoke (`/v1/industries`, one bundle) → traffic.
- No blue/green in v1; downtime window is seconds (container restart), documented in runbook.

## 15. Scalability Strategy

- v1 ceiling documented: 1 node, ~1,000 req/min, 10k items/day/channel.
- Cache: Redis response cache + ETag; `stale-while-revalidate` 300 s.
- Queue: Redis Streams single consumer group; scale by adding workers (same Redis).
- Triggers to scale: CPU > 70% or p95 > target for 7 days → move Postgres managed, add app node behind LB.
- Search: swap `SearchPort` to Meilisearch at > 100k articles (U13).
- DB: indexes from news-api §5; partition `articles` by month only if > 1M rows.

## 23. Technical Debt Prevention Strategy

- Debt ledger in `.work/plans/NEXT.md` "Done this iteration" notes + decision log.
- Refactor triggers: duplicate context logic, ORM leakage across boundaries, > 2 failed hotfixes in an area.
- No "temporary" TODO without an `UNKNOWNS` id or debt entry.
- Monthly dependency review; quarterly architecture review after GA.
- Contract changes go through versioned `/v2`, never in-place.

## 24. AI-Agent Execution Guidance

- One milestone per session; tasks in order; stop on gate failure.
- Danger zones (human approval or reviewer required): migrations, protected files (O4), auth/keys, prompt changes, retention purges, lead PII/consent changes, production deploy.
- Read before write: `.cursorrules`, HANDOFF, SPEC for the task, DIRECTORY_MAP.
- Model tier: `light` for docs/config, `standard` for CRUD/pages, `strong` for ingestion scoring, auth, migrations, bundle contract.
- Every task leaves evidence: command + exit code + file path; no "done" without validation.
- No cross-context imports; no new dependency without an ADR or UNKNOWNS entry.

## 25. Long-Term Maintainability Strategy

- Ownership: owner (product/ops), one engineering owner for API, one for web.

- Quarterly review: dependency upgrades, threat model, NFRs, cost.
- Succession: runbooks are the source of truth, not memory; onboarding = README → HANDOFF → one milestone.
