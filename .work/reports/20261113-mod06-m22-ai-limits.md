# MOD-06 — AI change risk, M22 reliable AI limits

**Scope of the diff:** M22 working tree — new Postgres usage ledger (migration `023`), the limit
module rewritten around tokens/requests/USD in day and month buckets, provider-client reservation and
halt/circuit-breaker handling, ingest attempt accounting, weighted-random desk rotation in the
scheduler, six new settings, six new admin-overridable keys, a `POST /v1/admin/ai/resume` endpoint, the
admin **AI spend** panel (caps, usage table, halt banner), EN/ES copy, the admin e2e spec, the OpenAPI
snapshot and `docs/ai-cost.md`, plus the migration-runner lock. 30 files, ~2,498 lines,
`blast-radius: high` (all in declared scope, `touch-scope-verify --strict` pass).

## AI change risk summary
- AI-assisted: yes (agent session, no `human-only` declaration).
- Boundaries crossed: 5 — (a) schema: one new table, no change to an existing one; (b) API: the admin
  AI payload gained fields and one new POST route; (c) worker: the refresh scheduler now rotates desks
  instead of starting every due desk; (d) web presentation: the admin AI tab; (e) platform: the
  migration runner now takes an advisory lock. No public read endpoint, auth, bundle or theme path
  changed.
- New cross-boundary deps: the spend ledger moved from Redis to Postgres, so every provider call now
  needs a writable database (the ingest path already did). `queue.py` gained an import of the existing
  `platform.overrides`; `offers` keeps importing `articles.infrastructure.ai_budget` as before. No new
  module boundary was crossed and no new external dependency was added.
- Test isolation: ok — `300 passed` in the api container (`ruff check`, `ruff format --check` 182
  files, `mypy src` clean, 130 files); web `pnpm lint`, `tsc --noEmit`, `pnpm check` (636 keys EN=ES, 5
  channels contrast) and `pnpm build` clean; `playwright test e2e/admin.spec.ts` **8 passed** including
  an axe WCAG 2.1 AA scan of the AI tab. New coverage: token/request/USD caps per bucket, day-before-
  month binding, ledger survival across a Redis flush, halt → refuse → resume, breaker expiry,
  unreadable-ledger denial, 401 halting after exactly one request, halted allowance = 0, rotation
  cardinality and staleness weighting, rotation-window hold-off, fail-open pacing marker, override
  round-trip for every new key, the daily-above-monthly refusal on both sides of the wire, and 4-way
  concurrent migrations against a throwaway database. `evidence: measured`.
- Two pre-existing defects surfaced by this verification and were fixed here, because both bear on
  "applies seamlessly in dev and prd": (1) `run_migrations()` had no lock, so the api and the worker
  migrating a fresh database together crashed one of them on `pg_type_typname_nsp_index` — reproduced
  on a scratch database, fixed with `pg_advisory_xact_lock`, and the new test **fails when the lock is
  removed** (mutation-checked); (2) the admin peak-calendar validation called `is_peak(utcnow())`,
  which returns early on a non-peak day, so a bad hand-edited calendar was silently kept at the
  weekend — it now parses the calendar directly and is tested across three clock positions.
- Live verification on dev against the revoked key: one direct call pair produced **1 provider
  request** then `ai.denied reason=halted:auth_401` with no second request; one full ingest run
  (`behavioral-health`, 80 items fetched, 2 new) recorded `summary_budget 28, summary_attempts 1,
  summarized 0, ai_stopped halted:auth` and finished `status ok`. The same run shape before this change
  sent **498 requests in 5 minutes**. Ledger after: `requests 2, tokens 0, cost 0, halted auth_401`,
  no stranded holds. `evidence: measured`.
- Human architectural review: **recommended**. This is the money path, and three decisions in it are
  product judgement rather than correctness: the default caps (300k tokens/day, 6M/month, 400
  requests/day, $0.25/day, $3/month), the rotation shape (2 desks per 60 minutes, staleness-weighted),
  and treating 401/403 as an indefinite halt that only an operator clears.
- Blast radius: if `reserve` is wrong in the permissive direction the stack overspends — the failure
  this milestone exists to end, and the reason the caps are denominated in tokens and requests as well
  as dollars. If it is wrong in the restrictive direction, summaries stop and stories publish with the
  source excerpt: the site stays up and nothing is lost. A migration failure stops the api and worker
  from starting (they run migrations at boot). The auth halt has no expiry, so a false positive stops
  all AI until someone resumes it — visible in `/admin` and in `ingest.ai_stopped`, but nothing pages
  anyone. `evidence: measured` for the request-bounding behaviour; `assumption` for the overspend
  direction, which no test can prove absent.
- Migration boot path: the advisory lock turns a crash into a wait. A pathological case — one backend
  holding the lock inside a very long migration — makes the other backend's boot slow rather than
  failed; no `lock_timeout` is set, and the lock is transaction-scoped so a dropped connection
  releases it. `evidence: measured` for both directions (race reproduced, then fixed and
  mutation-checked).
- Known transition gap: November's spend recorded in the old Redis ledger (dev: `$0.956`, keys
  `ai:spend:202611` / `ai:held:202611`, still present and now unread by any code) is **not** carried
  into the new `ai_usage` rows, so this month's caps start from zero. December is unaffected.
