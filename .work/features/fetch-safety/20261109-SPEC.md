## 1. Problem

The client is safe against SSRF and oversized payloads, and it currently retrieves 51 feeds with 3 errors in 308 polls. It is not safe against a publisher saying no. It presents a fake identity (`+https://system-news.example/bot`), never reads `robots.txt`, has no per-host pacing, no `Retry-After` handling, no backoff and no circuit breaker. With six concurrent fetches over the whole portfolio, one bad night against one host is indistinguishable from an outage.

The gap is not "can it reach sources today" — it is "does it behave well enough to keep reaching them".

## 2. Non-goals

- **No browser impersonation.** A Chrome UA and `Sec-Ch-Ua` set (as in `/mnt/work/Projects/fun/backend/app/acquisition/http.py:115`) exist to beat bot walls on public records. For RSS the honest crawler identity is the durable and defensible choice.
- **No headless browser fallback.** No feed in the portfolio needs JS. If one ever does, that is a separate decision.
- **No egress-region gate.** `/mnt/work/Projects/pizote/.../politeness.py` and `fun/.../egress.py` both carry infrastructure this project does not need: no jurisdiction-scoped sources, no VPN.
- **No schema migration.** Per-host state lives in Redis; losing it degrades to "unpaced for one cycle", never to a wrong fetch.

## 3. Requirements

### R1 — Identity

`USER_AGENT = f"{settings.bot_name}/{settings.bot_version} (+{settings.bot_url})"`, default `HeraldFoxBot/1.0 (+https://heraldfox.com/bot)`. One constant, imported by both fetchers (`articles/infrastructure/fetcher.py`, `offers/infrastructure/fetch.py`). No `example` domain may survive in either file.

*Accept:* `grep -r "example/bot" apps/api/src` returns nothing; the UA string in a live request resolves to the documented bot page.

### R2 — robots.txt

- Fetch `https://<host>/robots.txt` at most once per host per 24 h; cache the parsed `RobotFileParser` in Redis (`fetch:robots:<host>`, TTL 24 h with the raw body so a restart does not refetch).
- A missing or unreadable robots.txt means allow — the standard reading, and the correct one for feeds.
- `can_fetch(USER_AGENT, feed_url)` false → outcome `robots_disallowed`, `blocked=True`, **before** any request to the feed.
- Honour the declared `Crawl-delay` as the per-host floor for that host (raise the R3 floor, never lower it).

*Accept:* unit test with a robots body disallowing `/feed`; assert zero feed requests and outcome `robots_disallowed`. Test a `Crawl-delay: 30` body; assert the next request to that host waits ≥30 s.

### R3 — Per-host pacing

Redis hash `fetch:host:<host>`: `next_allowed_at`, `hour_count`, `hour_started_at`, `fail_streak`, `cooldown_until`, `cooldown_reason`.

- Floor between requests to the same host: 5 s (feeds are cheap; the scraper reference uses 30 s because it hits document endpoints).
- Hourly cap: 20 requests per host.
- Jitter: ±20 % on the floor so two instances do not align.
- A host under cooldown is skipped with outcome `rate_limited` and no request.

*Accept:* two sources on one host never overlap inside the floor (test with a fake clock); the cap holds at 21 attempts.

### R4 — Rate-limit response

`429` or `503`: no second request. Cooldown = max(`Retry-After`, `60 s × 2^(streak-1)`) capped at 6 h, plus jitter. `Retry-After` parses both delta-seconds and HTTP-date. A success or a definitive 4xx resets the streak.

*Accept:* test 429 with `Retry-After: 120` → outcome `rate_limited`, `cooldown_until ≥ now+120`; a second call inside the window makes no request.

### R5 — Failure streak and breaker

Five consecutive non-`ok` outcomes (timeout, connection error, 5xx) open the breaker for 30 min; the next attempt after that is a single half-open probe. `4xx` other than 408/429 does not trip the breaker — that is a feed problem, not a host problem.

*Accept:* six failures → breaker open; the seventh call is skipped; after 30 min exactly one request runs.

### R6 — Response hygiene

- Accept only `application/rss+xml`, `application/atom+xml`, `application/xml`, `text/xml`, `application/rdf+xml` (parameters ignored, case-insensitive). A missing `Content-Type` is tolerated only when the body parses as a feed.
- A `200` whose body matches an anti-bot challenge signature in the first 2 KB → outcome `challenge`, `blocked=True`, cooldown 1 h. Signatures: `just a moment` + `cloudflare`, `checking your browser`, `cf-chl-`, `incapsula incident id`, `request blocked` + `aws`, `g-recaptcha-response`, `are you a robot`.

*Accept:* test 200 + `text/html` + Cloudflare body → `challenge`, no parse attempt, no immediate retry.

### R7 — Redirects

Unchanged from today: manual, max 3, every hop re-validated (`fetcher.py:94-110`). A redirect to a non-public address stays `blocked`.

*Accept:* existing tests keep passing; add one hop that crosses hosts and assert the second host is paced independently.

### R8 — DNS pinning

`_resolve_is_public` currently validates one resolution and lets httpx resolve again at connect time (`fetcher.py:25-55`), which leaves a rebinding window. Pin the approved address: request the IP literal, send `Host: <hostname>`, and set `extensions={"sni_hostname": <hostname>}` so TLS still validates the certificate.

*Accept:* test with a resolver that returns a public address on the first call and `127.0.0.1` on the second; assert the connection targets the first address. If the transport rejects the extension, fall back to today's behaviour and record the residual window in `docs/source-quality.md` — do not silently drop the check.

### R9 — Observability

- Counter `ingest_fetch_blocked_total{reason}` with `reason ∈ robots|rate_limited|challenge|ssrf|size`.
- Gauge `ingest_host_cooldown_seconds{host}` (set on cooldown, 0 on success).
- Run stats gain `blocked`, `rate_limited`, `robots_disallowed`.
- A run whose blocked count exceeds 20 % of polls is status `partial` and logs one line naming the hosts.

*Accept:* a simulated 429 run surfaces in `/metrics` and in the admin run stats.

### R10 — Operator visibility

Admin Sources view shows `last_error`, `fail_streak` and `cooldown_until` with the reason. No new endpoint: reuse the existing source payload.

*Accept:* one seeded source in cooldown renders the reason.

## 4. Data and state

| Key | Type | TTL | Contents |
|-----|------|-----|----------|
| `fetch:robots:<host>` | string | 24 h | raw robots body + fetch timestamp |
| `fetch:host:<host>` | hash | 26 h | `next_allowed_at`, `hour_count`, `hour_started_at`, `fail_streak`, `cooldown_until`, `cooldown_reason`, `breaker_until`, `probe_pending`, `min_floor_s` |
| `fetch:host:<host>:lock` | string (SET NX) | 10 s | in-flight spacer for the floor |

Redis is already a dependency (`platform/cache.py`), so no new service. **Failure mode:** Redis unavailable → the fetcher runs unpaced, logs `fetch.pacing_unavailable`, and the run is marked `partial`. Never fail the fetch because pacing is down.

## 5. Outcome vocabulary

`ok`, `http_304`, `http_error`, `timeout`, `parse_error`, `too_large`, `blocked` (SSRF/redirect), plus `robots_disallowed`, `rate_limited`, `challenge`. `success` is `ok` or `http_304` (`ingest.py:173`); every other value counts as an error in run stats. `sources/application/quality.py:152` keeps its existing rule.

## 6. Test matrix

| Test | Asserts |
|------|---------|
| robots disallow | no request, `robots_disallowed` |
| robots `Crawl-delay` | floor raised |
| two feeds, one host | serialised with jitter |
| hourly cap | 21st attempt skipped |
| 429 + `Retry-After` | cooldown honoured, no retry |
| 503 without header | exponential escalation |
| breaker at 5 | open, probe after cooldown |
| 200 HTML challenge | `challenge`, 1 h cooldown |
| DNS rebind | pinned to first address |
| content-type `text/html` valid feed body | tolerated (parse decides) |
| redis down | fetch proceeds, run `partial` |
| UA constant | no `example` domain |

All in `apps/api/tests/unit/test_fetcher.py` with a fake clock and an httpx mock transport; no network in CI.

## 7. Rollout

1. R1 + R9 land first (identity and metrics, no behaviour change).
2. R3 + R4 behind `FETCH_PACING=enforce|shadow`; a week in `shadow` logs what it *would* have delayed before it delays anything.
3. R2, R6, R8 always on.
4. Then flip `enforce`, watch one full 12 h cycle, confirm the run duration and the error count against the 308-poll baseline.

Env additions: `BOT_NAME`, `BOT_VERSION`, `BOT_URL`, `FETCH_PACING`, `FETCH_HOST_FLOOR_S=5`, `FETCH_HOST_HOURLY_CAP=20`. Add them to `.env.example` only — never to a committed `.env.<env>`.

## 8. Risks

| Risk | Mitigation |
|------|------------|
| robots.txt blocks a legitimate feed | hard skip with a visible reason; the operator can disable the source, or the publisher can be asked |
| pacing makes a full refresh slower | measure before/after; 52 feeds at 5 s floor across ~40 hosts is bounded by the slowest host, not the total |
| Redis outage | fail open, mark the run partial, never fail a fetch |
| DNS pinning unsupported by the transport | documented fallback, residual risk recorded |
| changing UA affects hosts that key on it | the default is a new name; shadow mode surfaces any host that starts refusing |

## 9. Outcome (2026-11-10)

R1–R10 shipped in one pass, with four corrections found during verification:

- **C7 source repairs, not just retirements.** Two feeds are retired by the publishers' own robots policy — Finextra (`Disallow: /rss/` for `*`) and The Register (default-deny, licence required). Two parser corners are repaired instead, because the feed is otherwise legitimate: HTML-only entities (Inside Higher Ed) and a bare `&` in a title (Distribución Actualidad, `Óptica & Audiología`). The repair splits CDATA out before escaping, so a literal ampersand there is never printed as `&amp;`.
- **Financial was left below the source-policy minimum.** Finextra's retirement took the channel to 3 enabled sources against a minimum of 4. Added `Federal Reserve Board` (`https://www.federalreserve.gov/feeds/press_all.xml`, EN, trust 0.95) and applied the profile; financial is 4/4 again.
- **R9 gauge was not reset on success.** `ingest_host_cooldown_seconds` kept the last cooldown value after recovery; it now sets 0 on every non-cooldown outcome.
- **R10 reached the API but not the console.** `fail_streak`, `last_error`, `cooldown_until` and `cooldown_reason` were added to the source payload; the admin Sources table now renders the cooldown line and the last error.

Known gate weakness: `verify-sources` exits 0 even when a source fails (`summary.failed` is the only signal). It is not a clean pass/fail gate yet; the acceptance "exit 0" therefore proves nothing on its own. Recorded as a follow-up, not fixed here.
